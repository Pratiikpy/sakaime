# DiscoveryShift results

Generated by `tests/discovery/shift/run.ts` from `results.json`. The ground truth is sealed in `SEALED.md` (expected.json `3d55ebf819ad9207...`, cases.json `53d2a15f488042f6...`); the runner refused to score if either differed.

**What these numbers are.** Consistency results: the pipeline against a policy written from the construction of each mutation (`SEALED.md`). They show that the pipeline does what the policy says on layouts it was not tuned on. They do not show that the policy is clinically right, and the labeller is the pipeline's builder. 102 cases over four base sources (12 FDA clearances, 14 ClinicalTrials.gov studies, 11 reported-performance records, 30 bibliography records), so the number of independent clusters is four; the intervals below treat cases as independent and are therefore narrower than the evidence supports. 2 cases are known limits (undetectable from the response by construction) and are reported separately.

## How to read the runs

| Label | What it is |
|---|---|
| `run1` | The first run on the sealed suite. The model was called and every reply was recorded (`model-cassettes/`). Nothing had been changed after seeing a result. **This is the held-out measurement.** |
| `run2` | The recorded replies of `run1`, replayed offline through the code as it stands now, after the changes listed below. Deterministic: the offline judge path. |
| `replay-items-1-8` | The same replay at the code as it stood after items 1 to 8 below. It gives the same label as `run2` for every one of the 102 cases, so items 9 to 14 changed no decision on this suite. |
| `live2`, `live3` | The model called again, with no recording, so each is an independent sample of the model's behaviour. `live2` ran on the code of items 1 to 8, `live3` on the final code. |

Model-dependent arms are run more than once and the worst run is the one to quote. In every run of the full pipeline the false-accept count of scored cases is zero. What varies between independent model samples is small and is in the "Repeat runs" table: whether the model leaves an opaque column unmapped (correct) or maps it and the checks hold it (also correct), and whether a swapped identifier column is declined or held.

## Errata: everything changed after the first run

The protocol (`docs/06-evaluation-protocol.md` section 2) says rule changes made after the first held-out run are published, and that the cases they concern stop being held-out. Items 1 to 6 and 8 were made because of what `run1` showed; 7, 9, 10, 11 and 14 because of the live runs against Zetaris and the public APIs; 12 and 13 from reviewing the code. The tests that pin each one are in `tests/discovery/regressions.test.ts` and `pipeline.test.ts`, written from the general rule and not from the case.

| # | Change | Why | Effect on `run1` misses |
|---|---|---|---|
| 1 | The bare synonym `title` was removed from `study_title` | It collided with `article_title`: every bibliography with a `title` column was held because the name matcher said "study title" and the model said "article title" | D-C-01, D-I-01, D-I-02, D-N-01 (with item 8) |
| 2 | Name evidence also accepts the same words once the generic head noun is set aside (`article_name` for `article_title`); single common words inside a longer name (`device` in `device_class`) are no longer evidence | A renamed text column with an obvious name was held for lack of corroboration; the same rule had let `device_class` corroborate `device_name` | D-R-01, D-R-02, D-R-03 |
| 3 | A rejection whose evidence names its neighbour is tried once as the neighbour and checked in full (a target population filed as a study population, a development set as a study set, an identifier of another family, values that join to another field). If the name supports the original field and the values the neighbour, the result is a hold, never an automatic acceptance | The model filed `inclusion_summary` as `study_population`; the checks caught it and the whole source was declined | B-R-03, B-D-01 |
| 4 | A CSV that does not end with a line break is held | A cut that falls inside the last field leaves every row the right width, so only the missing final line break shows it | D-T-01 is held instead of registered; the sealed label says declined, so it is scored "imprecise" |
| 5 | Every value of a mapped text column is screened for instructions, and a column whose name tried to instruct the mapper is reported even when it was left unmapped | Only the first five values were screened; an instruction in row 7 of a title column would have been landed in a table that agents query | The lexical-only arm's false accepts A-X-02 and D-X-01 |
| 6 | The guard's patient-name pattern is ignored for public text (it fires on "Patient Decision Aid" in a title) | Found while testing item 5: 30 PubMed titles were held for "patient identifiers". MRN, date of birth and SSN patterns are kept | None on `run1` |

## What the ablations show

Each arm is run on the same sealed cases with the same recorded model replies.

- **Model off ("lexical").** Column names and identifier shapes alone map the cases whose headers are known names (34 of 48 must-map cases correct), and every case whose headers are plausible but unknown becomes a *partial* mapping: 14 wrong mappings, no false holds. The model is what turns a rename into a mapping. With the model off, two cases that need meaning to catch (a conflicting duplicate key, an instruction inside a value) slip through after item 5 (D-D-01, D-X-01).
- **Federated cross-source check off ("nojoin").** Without the joins against held records the pipeline cannot tell applicant names from device names, cannot see that identifiers do not join where overlap is expected, and cannot corroborate a text column: 16 of the 48 must-map cases are held for lack of corroboration, and the sealed cases A-I-03, A-W-01, A-Z-02 and A-Z-03 (trial numbers where submission numbers belong, applicant and device-name headers exchanged, identifiers that join to nothing or to half of what is expected) are registered. This is the output-changing role of the Zetaris catalog and the federated joins: they remove false holds and false accepts, and they are exercised through the same port in the live run.
- **Hardcoded extraction.** Fixed field names, strict casts. It fails the loader on every renamed layout, and loads without comment the cases whose names are unchanged but whose meaning is not: 32 of the 100 scored cases are false accepts, including every percent-scale and missing-value-code case. (It does cast-check, so a ragged CSV and an unparseable date fail it; a real extraction without even that would do worse.)

## Limits

- **Not independent.** The author of the cases, the labeller and the builder of the pipeline are the same person, and the class of every mutation was known when the validators were written. The cases (the particular aliases, values and combinations) were generated afterwards and not shown to the pipeline. A different labeller with mutations of their own is the missing test.
- **Four base sources.** The 102 cases are mutations of four tables built from records we hold. Statistics treat cases as independent; the effective number of clusters is four.
- **Known limits, run and reported, not scored.** A response cut cleanly after a complete record that declares nothing about its size (A-T-L1), and sensitivity and specificity headers exchanged where both columns hold plausible fractions (C-M-L1) are registered. No check on the values can tell either from the real thing. A model that reads domain knowledge into the headers does not help here, because the headers are what was swapped.
- **Held where declined was the sealed answer.** A-W-01, B-I-04, C-I-03 and D-T-01 are held for a person instead of declined. Nothing is registered either way; they are scored "imprecise" because the sealed label named one of the two refusals.
- **Distributions.** Checks cover range, scale, flags, repeated sentinels, identifier families and joins. A column whose values are plausible but drawn from the wrong distribution (an AUC of 0.2, a single repeated value) is not checked.
- **REST-table registration is not built.** Every source is registered as a normalised snapshot. A REST table re-issues its request from inside the engine on every query, cannot apply the conversions the checks recorded (a percent scale divided by 100, a date order), and would bypass the pinned fetch. The snapshot route is the one `docs/03-zetaris-plan.md` names for public JSON.
- **NOT VERIFIED.** Behaviour on a Zetaris build other than 2.4.3.1, on Linux or macOS, with concurrent users, with an API-key identity instead of the password login, or with a source larger than the 5,000-row, 2 MiB bound. The recorded replies are of the NVIDIA-hosted Nemotron route; the Nightshift route was not exercised by this suite.
