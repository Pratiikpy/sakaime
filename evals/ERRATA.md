# Evaluation errata

Dated entries, appended. Nothing here is edited after the fact; a correction is a new entry that points at the old one. Protocol: `docs/06-evaluation-protocol.md` section 2.

## E-001 (2026-10-27): the Gate 0 answer key was edited after the builder saw a dry run of the compiler

**What happened.** `evals/gate0/ANSWER-KEY.md` (section "Changes made after seeing a system output") discloses that, after the key and evidence items were written, a throwaway dry run fed the key's claims and hand-written evidence items to the in-progress `src/compiler`, and that the key was then changed in two ways:

1. **Evidence typing.** Analysis-population facts (age floor 22, pacing exclusion, 40 to 80 study ages) had been placed inside `authorization` items. After the dry run the items were split into an `authorization` item (what the indication says) and a `study` item (what the pivotal or validation study covered) for EyeArt (K200667 and K223357), GI Genius, Anumana and IDx-DR. In `evals/gate0/evidence-sets.json` that is the pairs `ev.ea.fda`/`ev.ea.fdastudy`, `ev.ea.k2`/`ev.ea.k2study`, `ev.gi.fda`/`ev.gi.study`, `ev.an.fda`/`ev.an.study`, `ev.id.fda`/`ev.id.study`. No expected label was changed by the split.
2. **CP-01.** The acceptable set was widened to include `CONTRADICTED_BY_SPECIFIED_EVIDENCE` after the dry run returned that label. The exact label stayed `SUPPORTED_ONLY_FOR_NARROWER_SCOPE`.

**Why it is contamination.** Under docs/06 section 2 a held-out label that the builders changed after looking at system output is no longer held out. Both changes moved the key toward behaviour the compiler had just shown.

**What git history can and cannot show.** The request was to list the change by diffing the key against history. That is not possible: `evals/gate0` appears in exactly one reachable commit (`535cad7`, 2026-10-27 11:10:26 +0530), which already holds the post-edit state. A dangling earlier commit (`dbf23d0`, 11:10:08, found with `git fsck --lost-found`) differs from it only by removed raw-terms and competitor-response files, not in `claims.jsonl`, `evidence-sets.json`, `ANSWER-KEY.md` or `tools/key-data.mjs`. So the edits happened in the working tree before the first commit and no earlier version of the key is recoverable. The description above is therefore the builder's own disclosure in `ANSWER-KEY.md`, cross-checked against the committed evidence items; the first encoding of the evidence is **NOT VERIFIED** beyond that disclosure.

**Treatment.** All 26 Gate 0 claims are **development**, never held-out, in every table of `RESULTS.md`. They keep their role in the Gate 0 80 percent rule because that rule's protocol (`evals/gate0/PROTOCOL.md`) was written with the claims as they are, and the rule is applied to the key as committed. Two sensitivity readings are reported beside it: the CP-01 score with the original acceptable set (without `CONTRADICTED_BY_SPECIFIED_EVIDENCE`), and the arms that use the hand-written evidence items (M1) kept apart from the arm that uses evidence extracted from the documents (M2), because only M1 depends on the item split.

**Replacement.** A new held-out set of 20 claims over five devices that no development claim uses, labelled before any system ran, sealed by hash: `evals/SEALED.md`.

## E-002 (2026-10-27): the extraction layer is not blind to the held-out documents

The five FDA summaries behind the held-out set are the five documents the extraction lead fetched to measure the FDA summary parser and then repaired it on (`tests/extraction/RESULTS.md`, "Documents the parser was not developed on", which states that the section is not a blind test). ## E-003 (2026-10-27): development of the evaluation adapter

The adapter that carries claims and extracted evidence into the compiler (`evals/lib/vocabulary.ts`, `evals/lib/pipeline.ts`) was iterated against the 26 development claims only. Its revisions are logged in `evals/results/adapter-log.json` with the development score at each revision. ## E-004 (2026-10-27): what the model arms did and did not do

- **B4 ran once, not three times.** The shared free-tier NVIDIA key allowed about two calls a minute for most of the session (HTTP 429 otherwise); a tool-using run is about five calls a claim. B3 ran three times on both partitions; B4 ran once on both. A second B4 run on the development set was started and abandoned part way; its recorded replies remain in `results/model-runs/b4.jsonl` as run 2 and 3 lines and are not used by any table. The development rows of B4 runs 2 and 3 in the first, discarded output were all HTTP 429 and are not reported.
- **A stray duplicate process** ran the held-out arm concurrently for several hours (a background chain restarted by an earlier kill). It wrote the same recorded replies to the same cache under the same keys (on load the earliest line for a key is used; the two replies to one prompt differed in a few cases even at temperature 0, which is the run-to-run variation the three B3 runs are there to show), so the held-out B4 run 2 lines in the cache come from it. It also changed the results once: one B3 call that had failed with HTTP 429 in the first held-out output was answered by this process, and a few prompts have two recorded replies. All tables were regenerated from the cache with the earliest-line rule and match a second replay exactly.
- **The prompts were not tuned.** The B3 and B4 system prompt was written once, checked on a single development claim for valid JSON, and hashed (`promptHash` in the results). Nothing in it was changed after the first full development run or after the held-out run.
- **Retries.** A call that returned HTTP 429, a 5xx or a timeout was retried with backoff; a reply, once received, was never re-asked. The harness client (not the product's 32 KB-capped client) was used for both arms because the records exceed 32 KB; the records are public FDA documents.

## E-005 (2026-10-27): changes made after the first held-out run, and what they did to the numbers

Three things changed after the held-out claims were first scored, and one of them is a regression the suite itself caused. The first committed results are 29b37e2; the next commit is 4ba053a; this entry and the suite fix come after.

**1. Adapter version 2.** `evals/lib/pipeline.ts` moved from version 1 to version 2 (adapter hash `1dd6f1ff2517` to `842836dce0e7`). The two changes: a study item in an FDA summary that states no date of its own is dated with the summary's decision date (`datesFromSameDocument`; the date is an upper bound on when the evidence existed, and the item records the inference), and the hospital's staleness window now applies to the authorization record as well as to dated study evidence (compiler rule R20, a design inference). E-003 says a later change to the adapter is a new erratum and a new run; this is both.

**2. The held-out run in `RESULTS.md` is a second look.** Under version 1 the sealed held-out claims scored 6/20 exact for the full pipeline (0/15 false-supported, 0/5 positive controls confirmed); the development set scored 8/26. The numbers now published are 9/20 (0/15 false-supported, 1/5 positive controls confirmed) and 9/26, from the pipeline after the adapter change and after the extraction and compiler began to read conditions, exclusions and diagnostic-use limits (`src/extraction/population.ts`, `src/compiler/conditions.ts`, `src/compiler/limits.ts`). They describe a pipeline that was changed after its first held-out score, on documents it was developed against (E-002). They are not a blind result. The first-run figures are kept here so the movement can be seen. Whether the changes were chosen with the held-out outcomes in view is **NOT VERIFIED**: the commit does not say, and nothing in the repository settles it.

**3. The conditions table.** `src/compiler/conditions.ts` places a claimed condition against the evidence's wording by a normal form, a curated synonym table (five entries: diabetes to diabetes mellitus, LVO, intra-abdominal free gas, LVEF, DR), one subtype entry (diabetic retinopathy below diabetes mellitus, from MeSH) and a closed list of narrowing words. It was written after the first held-out run. Each entry names the text it was taken from; the documents named are K200667, K223357, DEN180001, DEN170073, K253265 and K232699, all development documents, and no held-out document (K253801, K252360, K253825, K250680, K253163) is cited in the table or in the population reader. The table is small by design, so most real pairs go to a reviewer; that cost shows in the V rows as open population dimensions.

**4. The ScopeShift (A) regression and its cause.** At 4ba053a the suite scored 220/236 exact (93.2%) with 23/27 positive controls, down from 224/236 with 27/27 at 29b37e2, and new misses in `setting-widened`, `setting-unplaced`, `purpose-escalated`, `purpose-unplaced` and `age-min-lowered`. The cause was in the suite, not the compiler: the positive control copied the authorization's age and nothing else. Once the extraction layer read the conditions and exclusions of the indications, the authorization stated a condition the claim did not, and the compiler answered INSUFFICIENT_EVIDENCE because the claim named no condition (population unknown). Every mutation built from that control inherited the miss.

The fix (`evals/suites/scopeshift-a.ts`): the positive control copies the conditions and exclusions the evidence states (the study's own, plus the authorization's exclusions, in the world with a study). Where the authorization names a condition and the study record states none, no claim can be tied to both (a claim that names the condition finds the study's results unattached to it; a claim that omits it leaves the population undecided), so there is no positive control and the world is not built. That removes three worlds (DEN170073, DEN200055, DEN180001), 236 cases become 222, and the skipped list in the results file gains three entries with the reason. Result: 218/222 exact (98.2%), 24/24 positive controls, 0 of 198 false-supported.

This is a change to the construction made after seeing the compiler's answers, the same class of change as E-001. No expected label was changed. What changed is which cases exist and what the controls state.

The four remaining misses are all `purpose-escalated`: the authorization text of DEN200080, K253801, K252360 and K253163 itself limits diagnostic use, the compiler now reads that limit (REQUIRES_DOMAIN_REVIEW for a reservation, CONTRADICTED_BY_SPECIFIED_EVIDENCE for an exclusion), and the rule table expects a narrower scope. The table has no row for an authorization that limits diagnostic use. The misses are reported in `RESULTS.md` with the compiler's own reason and are not scored away. The twelve `date-past-window` cases that missed at 29b37e2 (0/12) now match (12/12) because R20 applies to authorization records.

## E-006 (2026-10-27): the compiler bounds a claim by the regulator's summary, and the evaluation does not exercise it

**What changed.** The compiler moved from 1.1.0 to 1.2.0 (`src/compiler/evaluate.ts`, `pools.ts`, `scope-ops.ts`). A study-typed item that the service takes from the regulator's decision summary (marked by a limitation line, `taken from the regulator's decision summary`) now bounds a claim on a dimension the authorization records leave silent, and on the open part of the population (the age floor, when the indications give the condition). It can only narrow what an authorization states. A registry entry or a publication never bounds, so any number of them cannot make a claim wider than the regulator's record contained. The request for a partly covered population is now a short sentence (what to supply for each part that falls short, three excluded groups in whole words and a count of the rest, how to restate the claim), and every non-contained dimension names which source limits the claim and quotes both values.

**Why, and a correction to the premise.** The defect was real: an EyeArt claim for ages 18 and older compiled SUPPORTED_FOR_SCOPE because ClinicalTrials.gov and PubMed state 18 and above. But the 22 does not sit in the authorization record. The authorization item states no age; the 22 is in a study-typed item of the same FDA summary (its pivotal analysis was of people aged 22 and older). The compiler already took the intersection of the authorization and the studies, so the union that hid the 22 was inside the study layer. The fix therefore adds a bounding layer for the regulator's own statements rather than changing the authorization/study intersection. This follows the authority matrix (the regulator record is authoritative for the population reviewed) and the earlier typing of those assertions as study (E-001) is kept.

**What the evaluation shows and does not show.** The marker is added where the service assembles evidence (`src/service/assemble.ts`). The evaluation adapter builds its items with `toEvidenceItems` in the extraction layer, which does not add it, so the new rule is not exercised by ScopeShift or by IdentityShift, TimeShift or FailureShift. The numbers did not move: ScopeShift (A) 218/222 exact, 24/24 positive controls, 0 of 198 false-supported; ScopeShift (B) V 9/26 on the development set and 9/20 on the held-out set, 0 false-supported. That is the absence of an effect on those sets, not evidence that the change is harmless or helpful there. The held-out run is again a second look (a compiler change after the first score, on documents the pipeline was developed against). The rule is tested where it applies: `tests/compiler/authority.test.ts` (property tests: a claim outside an authorization is never contained however many studies cover it; adding covering studies never makes it more contained; an authorization silent on a dimension restricts nothing; studies alone never give a supported label; the regulator's summary bounds exactly at its floor, never widens an authorization, and a registry entry never bounds) and `tests/service/pipeline.test.ts` (the EyeArt claim for ages 18 to 21 and the marker on the summary's study item).

**Limits.** The marker is a convention on the free-text `limitations` of an item, not a field of the evidence schema; a first-class `source` on the item would be sturdier and would let the extraction layer, and so the evaluation, apply the rule. Whether the regulator's analysed population should bound a claim at all is a design inference, tagged as such (`SAK-REGULATOR-BOUND`), and is open to clinician challenge.

## E-007 (2026-10-27): the evaluation adapter now applies the regulator-summary marker

**What changed.** `toEvidenceItems` (`src/extraction/to-evidence.ts`) takes an option, `regulatorSummary`, that marks study items as taken from the regulator's decision summary, the same marker the service adds in `src/service/assemble.ts`. The evaluation adapter (`evals/lib/pipeline.ts`, `evals/lib/scopes.ts`) now passes it for FDA summaries, so ScopeShift and IdentityShift exercise the E-006 rule.

**Effect.** None on any reported number: after the change and a full `--no-model` replay, ScopeShift (A) is 218 of 222 exact with 0 false-supported, and ScopeShift (B) is 9 of 26 on development and 9 of 20 on the held-out set, both with 0 false-supported. The claims in these sets do not test an age that only a regulator summary bounds, so the rule has no case to act on there. That is the absence of a test, not evidence about the rule; it is covered by the property tests in `tests/compiler/authority.test.ts`.

**Held-out status.** The held-out run remains a second look, for the reasons in E-002, E-003, E-005 and E-006.
